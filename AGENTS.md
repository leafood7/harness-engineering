- All project source, dependencies, tests, scratch files, and build artifacts belong under D:\VScodeProgects. This project root is D:\VScodeProgects\harness-engineering; Pi is the separate existing repository D:\VScodeProgects\pi.
- Work through complete authorized milestones; do not stop after small changes when independent work remains.
- Summary granularity follows substantial capability advances, not individual tasks, conversation turns, features, fixes, or check runs. Under D:\Obsidian\main\90-Templates\Harness Engineering, first find the existing summary for the same capability theme and update it. Create a new 数字_改动.md with the next integer only when a distinct, complete new capability represents a real advance; never automatically create a summary per development milestone or small change. Visual task management, unified execution records, and page recovery belong together in summary 11; subsequent related work updates that file. A finished project should not accumulate dozens of fragmented summaries.
- Each milestone summary explains what was done and added, significance, value and functionality, measured results, problems solved, technologies used, difficulties encountered, likely difficulties for the user, and next steps. Distinguish measured evidence from untested claims.
- Preserve existing changes in the Pi repository. Prefer public SDK/Extension interfaces in production; M0 source imports are validation scaffolding.
- M0 reproducible check: npm run verify:runtime. It uses an offline scripted model with actual Pi sessions and tools. Do not present it as evidence of live model quality or evolution benefits.
- M1 uses exact registry SDK dependencies from package-lock.json. Production adapters import public package exports, not neighboring Pi internal source paths.
- For code changes, run npm run check and relevant Node tests; run npm test for milestone acceptance. Preserve independent verification, state/event transactions, cancellation controls, and the distinction between task completion and export errors.
- M1 accepted baseline and test evidence are recorded in validation/task-execution/acceptance.json. Do not overwrite historical acceptance evidence merely to make a new change look passing; record new milestone results separately.
- M2 adds per-tool governance and approvals. Keep side-effect tools non-retryable, distinguish timeout from unknown outcomes, bind approval to exact arguments/target/policy, and atomically consume approval with attempt budget authorization.
- M2 acceptance evidence is recorded in validation/tool-governance/acceptance.json. Full regression covers 49 unique cases; an additional targeted audit check validates ask is not logged as granted permission. Preserve previous milestone records.
- M3 adds durable checkpoints, operation evidence, and explicit resume. Never treat message_end as already persisted; retain native Session snapshots at complete boundaries. Resume forks the saved Session, inherits cumulative budgets, and claims one child per source transactionally.
- Refuse unknown post-checkpoint side effects, unmetered model requests, uncertain verifier termination, workspace/artifact drift, and missing history. Never silently restart from scratch or inherit old approval receipts.
- M3 acceptance is recorded in validation/recovery/acceptance.json with 70 passing cases (49 regression + 21 new). Preserve historical milestone evidence. Run npm run demo:recovery for the self-contained owned-Worker crash demo.

- Current modules, tests, scripts and document filenames are named by responsibility. Historical validation manifests remain immutable and refer to their original paths. See validation/README.md.
- Context snapshots are frozen per Run and bound to checkpoints. Resume must not re-query current memory; reject modified snapshots. Do not treat extension callback exceptions alone as a reliable provider-request barrier.
- Memory is explicitly authored with source references, workspace isolation, bounded retrieval, revision checks, expiry and retirement. Never promote model claims or compaction evidence indexes into verified facts automatically.
- Run npm run demo:context for the local long-material demonstration; its output measures mechanisms, not live model quality.
- Context/memory acceptance: validation/context-memory/acceptance.json, 84 passing tests (70 regression + 14 new), plus 9 runtime compatibility checks. Preserve its evidence separately from historical baselines.
- Benchmark acceptance is separate from model capability: npm test validates mechanisms without paid calls; benchmarks/baselines/deepseek-flash-2026-11-02 records 32 real trials and independent audit. Never relabel scripted trials as live.
- Keep fixed task/verifier/runtime fingerprints and seeded paired trial order. Retain failed trials and separate memory-dependent information-availability cases from general-task claims. Do not overwrite published baselines or silently rerun selected failures.
- Benchmark results and experiences are append-only SQLite evidence; diagnoses remain unestablished and cannot become automatic policies. Raw Sessions, memory, and benchmark databases remain local under ignored artifacts.
- Before real provider dispatch, persist modelInFlight and check estimated remaining cost. A host rejection before dispatch must not invent uncertain provider usage; a genuinely interrupted dispatch must remain uncertain and block safe replay.
- Context capacity estimates exclude host-only details/usage/timestamp metadata; details may contain complete duplicate tool output. Preserve full native evidence while estimating provider-visible content.
- Current acceptance: validation/benchmark/acceptance.json; 99 passing tests (84 regression + 15 new), 32 live trials, 88 independently rerun fixed checks.

- User requires local-only work by default: do not git commit, push, create PRs, or publish to GitHub unless explicitly requested again. Local edits and validation remain authorized.
- Candidate experiment acceptance: validation/strategy-experiments/acceptance.json; 112 passing tests (99 + 13), 72 live tasks, 216 independent checks. Results remain local and uncommitted unless explicitly authorized later.
- Strategies are bounded profiles; stable.v1 is unchanged, candidates do not gain tools or budgets. Keep hypotheses, evidence references and frozen review policy. review_candidate is not adoption.
- Multi-prompt tasks share cumulative budgets; verify only after all prompts settle. Checkpoint prompt progress and strategy snapshots, skip fully completed prompts on resume, and refuse uncertain progress or strategy drift.
- Retention experiments must demonstrate native compaction before the final question and inspect actual pre-question context; answers must not leak through the root goal, seeded memory or external notes. Scripted responses need per-call timestamps for valid repeated native compaction.
- Read-correction acceptance: validation/read-correction/acceptance.json; 131 passing tests (112 + 19), 104 preregistered live trials plus a separate 12-trial schema confirmation, 324 independent checks. Keep both batches separate and preserve protocol-notes for the ambiguous original directory case.
- Bounded read correction is opt-in by strategy, at most two confirmed-no-effect EISDIR/ENOENT/ENOTDIR errors. It is not an automatic replay; preserve failed operations and isError=true, require genuine one-use host receipts, authorize and charge each new call, inherit used allowance on resume. Never extend this to writes, scope, permissions, timeout, cancellation or unknown effects.
- A successful follow-up read is not task success; final independent verification remains mandatory. Retention-over-limit failures are preserved rather than increasing quote limits after observing results.
- Keep frozen cost gates unchanged: anchored-correction.v1 exceeded the 25% estimated cost-increase gate in the main batch, so it remains a candidate. No automatic default switch.
- Since no Git commits are authorized, archive the exact runtime, selected cases and evidence/config recipe locally with scripts/archive-runtime.ts; never overwrite an existing snapshot. Model service state is not frozen.

- Functional strategy management uses src/strategy/store.ts and a separate per-state strategies.sqlite. Switch pointer and history atomically; preserve immutable version digests. New implicit tasks resolve once, explicit task profiles override, and resumed tasks retain the original version regardless of current selection. No automatic candidate adoption.
- Deliver functional milestones before any separately authorized benchmark campaign. Necessary correctness checks and final regression do not imply a new model evaluation. Never run Git staging, commits, pushes or GitHub operations without a fresh explicit user instruction.

- Queue jobs persist separately in queue.sqlite; freeze submitted config and node checker bytes. Queue job ID and Run ID are distinct. A transaction claims dispatch slots; never replay starting/running jobs after an uncertain crash. New scheduler adopts live workers and marks dead workers interrupted. Preserve explicit checkpoint recovery and cumulative budgets.
- Queue concurrency applies within one state root; serialize overlapping real workspace paths. Direct run, queue dispatch and resume share a per-state workspace lease for overlapping paths; queue slots remain queue-only. Other state roots are outside this protection. Uncertain tool or verifier outcomes must retain the lock until explicitly resolved. Scheduler stop only stops dispatch, while queue cancel cooperatively cancels a running task.

- Local dashboard lives in src/dashboard and apps/dashboard; serve only loopback, validate Host/Origin and per-process mutation tokens, allow only explicit static assets/API routes, redact known credentials, and render task data as text. Reuse queue/Run/verification authority; never fabricate completion percentages or bypass cancellation. Default data is one selected state root, not a scan of user directories.
- Dashboard UI uses buildless HTML/CSS/JavaScript with no added dependencies. Start with npm run dashboard; keep paid model campaigns separate. Close owned inspection servers and stop inspection schedulers at the end of browser QA.

- Unified dashboard records deduplicate queue/Run bindings and preserve separate recovery children and original terminal outcomes. Page recovery uses existing preflight, CLI detached launch and engine's atomic single-child claim; revalidate at launch, never replace recovery with fresh task submission. Preserve inherited cumulative usage and frozen strategy.
- New executions export a workspace observation after settlement, bound by workspace.observed file digest. File-change views validate the original manifest binding and use saved observations (or explicitly labeled checkpoint fallback), never scan a historical workspace's current content as task output. Observed changes do not imply verification success or causal attribution.

- Visual task creation is part of summary 11. Drafts in src/dashboard/creation.ts are strict schemas, validate against the existing Task contract, scope real workspaces, use the pinned offline model catalog, and reference environment variable names only. Revalidate on submit and enqueue through QueueStore; checking and saving templates never dispatch a model or execute a checker.
- Templates are append-only local configuration snapshots; saving does not imply runtime readiness. Reloaded drafts must pass current workspace/model/key/verification checks. The offline form mode is explicitly a fixed file-writing exercise, never a model that understands arbitrary goals. Retain advanced JSON task import.

- Dashboard management preserves immutable historical text snapshots and verifier evidence bound to SQLite event digests. Never substitute live workspace content for missing historical bytes. Preserve bounded capture and explicit omissions.
- Submission and edit receipts commit atomically with queue changes; copied-task provenance is committed with queue creation. Queued edits use optimistic configuration hashes and cannot modify started jobs. Template family names can change; version configuration snapshots remain immutable.
- Dashboard startup stops further dispatch by incompatible/unknown-version schedulers without terminating existing workers. Draft clocks and cleanup tombstones prevent delayed autosave from restoring cleared data. Cleanup never deletes run, session, checkpoint or output evidence.

- Execution experience is adapted from the explicitly authorized local evolving-harness reflection and batch modules; exact source fingerprints are in docs/local-reuse.json. Keep evidence packets scoped, bounded and digest-bound to original Run/event/feedback records. Validate every proposal before any insertion, preserve typed provenance, deduplicate exact inputs and retain optimistic revisions/history. Reviewed suggestions never automatically become facts, memory, active strategy or evidence of improvement. No automatic provider requests, benchmarks, activation or Git actions.
- Experience and improvement-suggestion work is one capability theme. Update summary 12 for related follow-up work rather than creating a summary for each feature or fix. Keep visual task management summary 11 separate from this new execution-experience capability.
